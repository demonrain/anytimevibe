# 随码（AnytimeVibe）与 Paseo 对比分析

> 更新时间：2026-08-18  
> 对比对象：当前仓库 `anytimevibe` vs 开源项目 [`getpaseo/paseo`](https://github.com/getpaseo/paseo)（基于其 README / architecture / security 等公开文档）

## 1. 一句话定位差异

- **随码（AnytimeVibe）**：偏「远程任务接力产品」，强调手机上续跑本机 AI 编程任务、审批、推送、主机配对与多用户隔离。
- **Paseo**：偏「通用 Agent 编排平台」，强调本地 daemon + 多客户端 + 多 agent 协作、CLI 自动化、SDK、可扩展工作流。

## 2. 架构对比（核心差异）

| 维度 | 随码（AnytimeVibe） | Paseo |
|---|---|---|
| 核心拓扑 | Web PWA + VPS Relay + 桌面 Agent（本机执行 CLI） | 本机 Daemon 为核心，桌面/移动/CLI 连接 Daemon，Relay 可选 |
| 远程连接方式 | 默认通过中继做配对和消息路由 | 可 Relay，也可直连（TCP/VPN/Tailscale） |
| 数据持久化 | 服务端 PostgreSQL（账号、主机、配对、密文事件） | 以本机 daemon 持久化为中心（文档描述为本地存储） |
| 客户端模型 | 浏览器 PWA + Electron Agent（双端分工清晰） | 移动/桌面/CLI 都是一等客户端，统一连 daemon |
| 产品边界 | 明确不做任意终端/远程桌面/文件浏览器 | 更偏通用编排，终端/调度/子 agent 工作流更丰富 |

## 3. 能力矩阵对比

| 能力项 | 随码（AnytimeVibe） | Paseo |
|---|---|---|
| 多引擎接入 | Codex / Claude / Grok / Cursor / Antigravity（五引擎） | Claude / Codex / Copilot / OpenCode / Pi 等 |
| 手机端续任务 | 强（产品主线） | 强 |
| 任务审批流 | 强（移动端审批 + Push） | 有权限与交互机制，但产品重心更偏编排通用性 |
| 多用户与管理后台 | 有（注册、封禁、审计） | 文档侧重个人/团队编排，后台治理不是主卖点 |
| CLI 自动化能力 | 有接力/本地流程，但不是平台主轴 | 强（daemon / agent / schedule / workspace 指令完整） |
| 定时任务/计划任务 | 当前不是核心能力 | 强（schedule / loop 等） |
| SDK 生态 | 当前偏产品内聚 | 强（`@getpaseo/client` 面向集成） |
| 工作区隔离策略 | 白名单 + 单任务绑定 | worktree/workspace 编排能力更重 |

## 4. 随码（AnytimeVibe）的优势

1. **产品闭环更完整（面向“可交付”）**  
   从注册、配对、任务下发、审批、通知、接力到自动更新，用户可直接落地上线给团队使用。

2. **移动端任务体验设计更垂直**  
   不是泛化控制台，而是围绕“离开工位继续推进任务”做过交互取舍（审批、任务状态、Diff、接力）。

3. **治理能力更贴近多人服务场景**  
   多用户隔离、管理员后台、封禁与审计在 SaaS/私有部署中实用价值高。

4. **本机执行 + 白名单约束边界清晰**  
   安全边界表达明确，风险面可解释，便于对外沟通与部署审批。

## 5. 随码（AnytimeVibe）的短板

1. **Codex 长进程配置热加载复杂度高**  
   由于 app-server 缓存配置，切号热更新和旧会话继承容易出现边缘问题（你这次遇到的就是典型例子）。

2. **平台化抽象不如 Paseo**  
   当前更像“产品型方案”，在 agent-to-agent 编排、任务调度、可编程扩展（SDK）方面不如 Paseo 平台化。

3. **对中继拓扑依赖较强**  
   与“可选直连 daemon”相比，网络拓扑灵活度和本地完全自治能力略弱。

4. **生态与社区扩展面相对窄**  
   插件、第三方工具链对接、自动化脚本生态尚有提升空间。

## 6. Paseo 的优势

1. **平台化能力强**：daemon 中心化、CLI 全量化、SDK 化，适合集成与自动化编排。  
2. **多客户端一致性强**：桌面/移动/CLI 都是一等入口。  
3. **可扩展工作流成熟**：调度、子 agent、workspace/worktree 等机制更系统。  
4. **“编排层”定位清晰**：不替代引擎，重在把不同 agent 组织起来。

## 7. Paseo 的短板（相对随码）

1. **产品化交付路径不一定更短**：对“直接给团队上手”的场景，随码当前功能组合更聚焦。  
2. **治理后台能力不是主线**：对账号体系、审计、运营治理的现成功能不如随码聚焦。  
3. **学习曲线偏平台化**：对只想“手机续跑本机任务”的用户，概念层更重。  

## 8. 适用场景建议

### 更适合选随码

- 你要的是**“远程接力产品”**，而不是“通用编排底座”。
- 你有明确的移动审批/通知需求，且需要多用户管理能力。
- 你希望部署后即用，减少额外平台搭建与二次集成。

### 更适合选 Paseo

- 你要把 agent 编排作为**平台能力**（脚本化、调度、SDK 集成）。
- 你有复杂多 agent 协作、自动化流水线、跨终端深度控制需求。
- 你更看重可扩展生态而非现成的业务闭环。

## 9. 对随码的演进建议（参考 Paseo 的长处）

1. **增强“编排层”能力**  
   增加任务模板、计划任务（cron）、子任务并行编排，形成可复用工作流。

2. **补齐可编程接口**  
   增加稳定的本地/服务端 API 或 SDK，便于外部系统触发任务和查询状态。

3. **降低 Codex 热切号不确定性**  
   - 将“配置指纹一致性检查”前置到每次 turn 发起  
   - 增加“生效配置可视化”（当前 provider/base/key 来源）  
   - 增加“一键重载引擎路由”按钮与诊断页

4. **连接模式分层**  
   在现有中继模式外，考虑补充“可选直连/VPN 模式”，满足更严格内网场景。

## 10. 结论

- **随码当前更像“可上线的远程 AI 编程任务产品”**：在移动接力、审批闭环、多用户治理方面有明显优势。  
- **Paseo更像“面向未来的 agent 编排平台”**：在平台化、自动化、扩展性方面更强。  
- 如果你的目标是“让用户今天就能离开电脑继续推进任务”，随码路线是对的；如果目标升级为“做 agent 编排操作系统”，可借鉴 Paseo 的 daemon/CLI/SDK 设计进一步升级。
